# 03 — UI

## Purpose

Guide UI work without imposing a fixed visual identity. When design is unclear, run a **protocol of questions** covering controls, structure, and aesthetic systems.

## When this module applies / when to skip

- Applies: any user-visible interface work.
- Skip / `N/A`: API-only, CLI-only without UI, or backend-only tasks with zero presentation surface.
- If a task might add UI later, keep awareness and ask before inventing screens.

## Hard rules (MUST / MUST NOT)

- MUST NOT invent a brand-new visual identity when the project already has one — match it.
- The conversation line-split in `00-core.md` (Language) applies only to chat replies. It does not set product layout direction.
- When the confirmed product locale is Arabic or another right-to-left language, MUST set the user-facing UI direction to right-to-left.
- MUST use the platform’s current official direction mechanism. Before naming an attribute, property, or API, follow **Current sources** in `00-core.md`.
- MUST NOT satisfy the direction rule by splitting Arabic and English onto separate lines inside the product UI.
- When the locale direction is unknown, ask. Do not assume left-to-right.
- MUST NOT assume a fixed look (no mandatory glassmorphism, neumorphism, flat, etc.).
- When design is unclear, MUST ask via question protocol about:
  - buttons / CTAs
  - icons (in-UI glyphs — not the same as app/product identity icons)
  - menus / navigation
  - containers / sections / layout
  - aesthetic system (flat, material-like, glassmorphism, neumorphism, brutalist, system-native, etc.)
- For **app / product identity icons**, favicons, launcher icons, PWA/store assets, or user-changeable icon packs, MUST follow `17-branding-and-icons.md` (do not invent sizes, platforms, or static vs changeable strategy here).
- MUST keep the first meaningful viewport focused (avoid dashboard clutter on non-dashboard pages) unless project design system says otherwise.
- MUST ensure desktop and mobile usability when the product targets both.
- MUST NOT add decorative complexity that fights existing patterns.
- During/after build: ask only when UI choices are ambiguous.

## Question protocol

### Example — Aesthetic system

```markdown
### Question
Which UI aesthetic should this surface follow?

1. Match existing project design system / components — **Recommended**
2. Clean flat / utilitarian
3. Soft depth (subtle shadows, no heavy glass)
4. Distinct style (glassmorphism / neumorphism / other — specify in custom)
5. Other: _______________

Hints:
- Recommended whenever shared components or screens already exist.
- To decide: inspect existing screens and component library tokens.
```

### Example — Navigation pattern

```markdown
### Question
How should primary navigation be structured?

1. Top bar with key sections
2. Side navigation (desktop) + compact mobile nav — **Recommended**
3. Tab bar (app-like)
4. Minimal — single flow, almost no nav chrome
5. Other: _______________
```

### Example — Button hierarchy

```markdown
### Question
What button hierarchy should we use on this screen?

1. One primary CTA + secondary text/outline actions — **Recommended**
2. Two equal-emphasis actions
3. Icon-only actions with labels in menus
4. Menu-driven actions; few persistent buttons
5. Other: _______________
```

### Example — Containers / sections

```markdown
### Question
How should content be grouped?

1. Simple stacked sections with clear headings — **Recommended**
2. Carded groups (only where interaction needs a container)
3. Dense table/list first; detail on drill-in
4. Wizard / stepped sections
5. Other: _______________
```

## New-project workflow

1. Confirm platforms and whether a design system exists.
2. Ask aesthetic, navigation, and CTA questions as needed.
3. Define tokens lightly (color, type, spacing) in PROJECT-SPECIFIC — do not over-specify.
4. Build UI only after blocking UI questions are answered (or deferred once).
5. Prefer reusable components over one-off markup.

## Existing-project workflow

1. Inventory existing UI patterns before proposing new ones.
2. Treat visual inconsistency as a defect unless product wants a deliberate redesign.
3. Quick cosmetic fix only if isolated; otherwise align to system-wide patterns.

## Post-change checklist hooks

- [ ] Matches existing identity or agreed new direction
- [ ] Navigation/CTA choices intentional
- [ ] No unexplained new aesthetic system
- [ ] Responsive behavior considered
