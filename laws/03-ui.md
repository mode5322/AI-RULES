# 03 — UI

## Purpose

Guide UI work by matching the interface the project already has. Do not open a questionnaire for controls, layout, or visual style.

## Status

`ACTIVE | N/A | PROJECT-SPECIFIC` → default: `PROJECT-SPECIFIC`


## When this module applies / when to skip

- Applies: any user-visible interface work.
- Skip / `N/A`: API-only, CLI-only without UI, or backend-only tasks with zero presentation surface.
- If a task might add UI later, keep this file and do not invent screens until the user asks for one.

## Hard rules (MUST / MUST NOT)

- MUST NOT invent a brand-new visual identity when the project already has one — match it.
- Conversation Arabic mixed-script marks (`00-core.md` Language, fixed) apply only to chat replies. They do not set product layout direction.
- When the confirmed product locale is Arabic or another right-to-left language, MUST set the user-facing UI direction to right-to-left.
- MUST use the platform’s current official direction mechanism. Before naming an attribute, property, or API, follow **Current sources** in `00-core.md`.
- MUST NOT satisfy the direction rule by splitting Arabic and English onto separate lines inside the product UI.
- When the user designs a button, a form, or a screen, register it in **System design → UI components** and implement it once.
- The component MUST be flexible: label, action, and state that differ between uses are inputs.
- MUST reuse that component later. MUST NOT duplicate the element for each screen.
- MUST NOT assume a fixed look (no mandatory glassmorphism, neumorphism, flat, etc.).
- Match the project's existing buttons, icons, navigation, and layout. Do not open a visual questionnaire.
- For **app / product identity icons**, favicons, launcher icons, PWA/store assets, or user-changeable icon packs, MUST follow `17-branding-and-icons.md` only when that work is the current task.
- MUST keep the first meaningful viewport focused (avoid dashboard clutter on non-dashboard pages) unless project design system says otherwise.
- MUST ensure desktop and mobile usability when the product targets both.
- MUST NOT add decorative complexity that fights existing patterns.
- During/after build: ask only when the current screen cannot be built from the existing UI.

## Question protocol

Ask from this file only when the current task needs this module and the repo does not already show the answer. Follow `templates/question-protocol.md`: one short line in the user's language, and the option list only after «عرض خيارات» or "Show options". Store an Arabic answer in English. Do not add a fill-in setting in this file.

## New-project workflow

1. Read the platforms and design system the repo already has.
2. Do not ask aesthetic, navigation, or button questions.
3. Match existing color, type, and spacing. Do not open a token questionnaire.
4. Build the screen from components already registered. A new button, form, or screen is registered once, then reused.
5. Do not copy an element for each use. Pass what changes as inputs.

## Existing-project workflow

1. Inventory existing UI patterns before proposing new ones.
2. Treat visual inconsistency as a defect unless product wants a deliberate redesign.
3. Quick cosmetic fix only if isolated; otherwise align to system-wide patterns.

## Post-change checklist hooks

- [ ] Matches existing identity or agreed new direction
- [ ] Navigation/CTA choices intentional
- [ ] No unexplained new aesthetic system
- [ ] Responsive behavior considered

## PROJECT-SPECIFIC

No fill-in settings live here. Behavior and System design are only in `templates/project-profile.template.md`. If this module does not connect to the current project, do not ask about it.
